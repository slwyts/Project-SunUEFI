# 发布要求

源码公开和二进制发布是两件事。当前仓库提供源码和 CI 构建产物，正式发布前需要完成以下核对。当前支持情况见[项目状态](../status.md)。

## 公开源码前

* 检查要提交的文件和 Git 历史中是否有个人信息、凭据、设备标识和无权分发的内容。
* 完成原创代码、第三方库、字体、固件和生成内容的许可与署名清单，见[第三方来源](../../THIRD_PARTY.md)。
* 确认公开的依赖仓库和提交都能取到，并在全新克隆下运行主机检查，见[测试与检查](testing.md)。
* 说明完整构建需要哪些本地输入，见[本地输入](local-inputs.md)。

## 发布二进制前

每个发布版本要对应明确的源码提交、配置清单和 SHA256 哈希，主机检查需要全部通过（`./build.sh check`）。发布说明中逐项写明：

* 哪些功能可用，哪些不可用；
* 适用的设备型号和系统版本；
* 明确的回到 Android 的方法；
* 各启动路径的核对结果：

| 启动路径 | 发布前需核对 |
| --- | --- |
| 临时 `fastboot boot` | 实际发送的镜像、菜单显示、后台服务、退出并回到 Android |
| 合体 BOOT 启动 Linux | 内核与模块版本匹配、ESP 读取、系统交接、桌面正常启动、返回 Android |
| Recovery 模式 | 不使用独立的 Recovery 镜像，原厂 Recovery 不受影响，见[故障恢复](../user/recovery.md) |
| 标准 EFI 引导 | ExitBootServices 安全退出、运行时服务，与现有 ARM64 原始交接是不同路径 |

原厂已有的硬件功能用同一台设备对照，核对耗时、输入响应和故障后的恢复。
例如 Fastboot 使用同一接口、线材和镜像，分别记录上传、写盘和读回；
长操作期间检查键盘、触控板和触屏。原厂不提供的功能按相应标准验收：
UEFI 用标准引导程序和变量工具，系统更新用发行版的包管理器实际安装、升级和回退。

1.0.0 使用 Linux 7.3.3。发布前要在平板上验证桌面的电源设置、拔线后的
挂起与唤醒，以及插电后熄屏且继续充电。磁盘休眠、原生相机 3A 和拍照闪光
不列为这次发布的要求。

### 标准 UEFI 启动与存储

ESP（EFI 系统分区）内已有官方 `ukify` 和 ARM64 systemd-stub 生成的标准 UKI。
产品默认安装 systemd-boot；固件按 `BootNext`、`BootOrder` 和 `Boot####`
选择 EFI 应用，设备后备路径复用上游库。SimpleInit 作为普通启动项注册；
其“启动 Linux”按系统启动顺序执行。Linux 运行时的变量持久化另行处理。

| 工作 | 现在的实现 | 下一步 |
| --- | --- | --- |
| 固件启动顺序 | 实机确认 `BootNext` 在运行前删除；一次性 EFI 程序返回错误后按 `BootOrder` 进入 systemd-boot，重启没有重复执行 | 核对从固件设置重新排序、取消选择后仍按用户顺序启动 |
| SimpleInit 与一次性选择 | 平板已注册置顶的 SimpleInit `Boot####`，菜单可继续启动现有 SteamOS | 用实体键盘和侧键核对 Esc 选择、取消与顺序恢复 |
| 系统发现与直接启动 | 固件复用 UEFI 库解析启动路径。ARM64 虚拟机上的两块 GPT ESP 有同名后备文件，完整路径和短分区路径均只启动指定分区 | 在平板用内置 ESP 和 USB ESP 复测一次性启动与回退；检查直接 UKI 和其他加载器的资源退出 |
| 引导程序 | 官方 systemd-boot 已在现有 SteamOS 实机启动分离文件与旧 UKI，已设置三秒菜单。ARM64 虚拟机通过 Debian 签名 APT 升级引导程序；Valve 原装 `bootctl` 在双 ESP 测试中只更新目标分区 | 在平板检查 Debian 和 SteamOS 升级后的冷启动、用户排序与另一启动器；用两代 Valve 包验证 pacman 升级 |
| 标准存储写入和 Fastboot 刷写 | 扫描不改 GPT，刷写只卸载目标。平板上已完成 512 MiB sparse 写入、全量读回与取消读取后的自动恢复 | 对照同机原厂继续优化传输和连续写入速度；实测长操作中的触屏、键盘和触控板 |
| 系统运行时 EFI 变量 | 固件在 Boot Services 阶段把变量保存到 `persist/sunuefi/`；Linux 的 `efivarfs` 可读，固件运行时不支持写和删除 | 为固件 `SetVariable()` 接入与系统 UFS 有明确仲裁的持久化服务；用标准 `efibootmgr` 核对创建、排序、一次启动、删除和断电保存 |
| EFI 层分区管理 | 未实现 | 先完成标准块读写和 GPT 安全检查；“伪动态分区”只有需求方向，未实现，不改变现有分区布局 |

默认 UKI 名称应描述 Linux，而不是固件 SunUEFI；最终由标准安装工具按安装标识
和内核版本管理，不能把另一固定名字变成固件前提。SimpleInit 仍随产品提供
默认设置，其他系统可以自行命名、安装和更新 EFI 文件。

### 原生 Windows 11 ARM64

`woa` 分支在同一份 SunUEFI 上开发 Windows 支持。Windows 通过 ACPI
获取硬件描述，Linux 仍从设备树启动。改动共用固件后，在设备上检查
systemd-boot、Linux 睡眠唤醒和返回 Android；安装 Windows 只使用明确
选定的独立系统空间，不让安装程序重新分配整块 UFS。

平板已用这份带 ACPI 的固件经 systemd-boot 启动 Debian。EFI 系统表
给出 ACPI 2.0 指针，从设备读回的 XSDT、FADT、DSDT、MADT、GTDT 和 PPTT
校验和均正确；Linux 的 PSCI 仍从设备树初始化。IORT 使用原厂 XBL 的
SMMU 中断和设备映射：UFS 的 StreamID 为 `0x60`，USB 为 `0x40`。微软原版
ARM64 介质自带的 `storufs.inf` 优先匹配 `ACPI\QCOM24A5`；固件另外通过
`_CID` 提供 UFSHCI 类兼容标识 `PCI\CC_010901`。仅靠 `_CLS` 分类不会在这版
WinPE 里选中通用驱动。启动文件由固件读出；要证明 Windows 已接管
控制器，须在 WinPE 内读写内置卷，不能以看到引导菜单或 INF 匹配代替。

| 功能 | 发布前在 Piano 上检查 |
| --- | --- |
| 内存 | 各容量机型使用同一镜像。核对 SMBIOS 装机容量与原厂 DDR 数据，再核对 WinPE 的 `memory.txt`；Windows 的可用段不能跨越物理空洞或占用硬件保留区。 |
| 启动与存储 | WinPE 能接受键盘输入，从 Windows 的存储驱动读取 UFS，并在目标卷写入、读回文件。完整 Windows 从内置存储连续冷启动，更新后仍能启动，也能返回 Android。 |
| GPU 渲染 | 分别用 D3D11 和 D3D12 绘制并读回已知画面。记录 DXGI 选中的适配器，用 GPUView 对应到实际执行的硬件队列；WARP 软件渲染、固件帧缓冲和设备管理器的名称都不能替代这一检查。 |
| 内屏与应用 | 检查桌面合成、浏览器和实际 3D 应用的画面、帧时间及持续负载下的频率和温度。视频硬件解码单独检查。逐项实测驱动报告的显示模式、亮度、熄屏唤醒；不因能显示开机画面就宣称支持高刷新率或 HDR。 |
| 驱动维护 | 从原版 Windows 安装驱动，检查睡眠唤醒、图形设备重置、驱动升级、回退和卸载。正式安装使用 Driver Store，不替换 Windows 自带的图形 DLL。 |
| 其他硬件 | 用普通应用检查触摸、键盘和笔、联网和配对、音频、旋转、相机和指纹。确认插电熄屏继续充电，拔线睡眠可唤醒；记录睡眠前后的设备状态和电量。 |

用 `./build.sh windows graphics-test` 构建 ARM64 测试程序，在 Windows 运行
`graphics-readback.exe --list` 列出图形适配器。选定本机 Adreno 的
LUID 后运行 `graphics-readback.exe --luid 高位:低位`，分别检查 D3D11 和
D3D12 的命令完成与结果读回。CI 中的 `--warp` 用微软软件适配器校验测试
程序本身，不能计作平板的硬件结果。

在已装 WDK 的 Visual Studio 开发者终端，用 `./build.sh windows drivers`
构建 ARM64 内核驱动部件。使用 LLVM 交叉编译时，传入 `--kit-include`
及 WDK 中包含 `km/`、`shared/` 的版本目录；分开安装的 SDK 和 WDK 可分别
传入。`adreno.lib` 按本机 GPU 固件的要求给 GMU 分配内存和命令队列，通过 Windows
的 IOMMU 接口只映射 GMU 使用的页，不占用渲染引擎的地址空间。真机启动还需要 ACPI
描述正确的 DMA 映射、供电和复位，以及能绑定到设备的显示驱动；静态库本身不能安装。

键盘套的 `wn8030.sys` 是 ARM64 KMDF 驱动。它从 Windows 获取 I²C 和 GPIO
资源，冷启动时加载键盘控制器固件，通过同一个 HID 设备上报键盘和触控板输入。
键盘套吸附后每 12 秒续供电，设备进入低功耗状态时停止。这个构建产物尚未签名；
还需为板上的控制器提供准确的 ACPI 标识及配套 INF，才能在平板的 Windows 上安装并检查输入。

存储部件 `ufs.lib` 将 Windows 的 SCSI 请求转换成 UFS 命令，用 Storport 分配的
DMA 地址提交读写并处理完成中断。它使用 ACPI 报告的寄存器范围，不按 PCI 设备查找。
平台打开时钟并初始化 PHY 后，驱动建立标准 UFS 链路，通过 `REPORT LUNS` 查找设备实际提供的
逻辑单元。独立控制器模型已验证：即使唯一的盘编号为 7，也能从冷启动完成写入、刷盘和读回。
板级代码按本机原厂参数校准两条 UFS 通道，不复位仍然工作的链路。它还不是平板的
Windows 启动盘驱动：进入和退出低功耗状态时需要 Windows 管理共享电源与时钟，
再由可安装的 Storport 驱动接管内置存储。

GPU 的同芯片驱动与本机原厂基线见[上游项目](upstreams.md)。在另一部
SM8750 设备上的测试结果只用来选择实现，不计入 Piano 的发布结果。

ACPI 描述的 GPU 和 GMU 共享一个设备节点，显示控制器是另一个设备。
使用同一版微软 WinPE 对照两个不同的 `_HRV`，Adreno 830 对应的硬件 ID 为
`ACPI\VEN_PRP&DEV_0001&REV_44050001`。不要用通用的 `ACPI\PRP0001` 匹配显卡；
其他同样使用设备树兼容描述的硬件也会带这个 ID。枚举验证不等于驱动已经绑定或开始渲染。
