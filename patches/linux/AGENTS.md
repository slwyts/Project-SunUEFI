# 下游仓库的Linux内核补丁维护要求

所有 Linux 内核补丁按以下顺序分类、排列并连续编号。同一类别内按依赖关系排序。上游补丁所需的必要上游前置补丁应一并回移，排在依赖它的补丁之前，不依靠后续本地补丁补齐其编译前提。

1. 已被 Linux 主线、stable/LTS 维护树或对应子系统维护者集成树接受的补丁，文件名使用 `00xx-UPSTREAM-TITLE.patch`。补丁中通过 `Link:` 给出包含完整提交哈希的上游 commit 链接，并保留原有相关链接。接受状态必须有实际集成提交作为依据，仅有 `Reviewed-by`、`Acked-by` 或准备应用的回复不算已接受。
2. 已在 Linux 相关邮件列表发布、尚未被上游接受的补丁，文件名使用 `00xx-MAILLIST-TITLE.patch`。补丁中通过 `Link:` 给出所采用版本的具体邮件链接，优先使用 `lore.kernel.org` 的 Message-ID 链接，不使用搜索结果页或仅指向 cover letter 的链接。
3. 来自其他项目仓库的补丁，文件名使用 `00xx-EXTERNAL-TITLE.patch`。补丁中通过 `Link:` 给出原仓库的具体 commit 链接，不使用可变的分支链接。
4. 本项目自行撰写、尚未投稿或被上游接受的补丁，文件名使用 `00xx-LOCAL-TITLE.patch`。

分类前缀只用于补丁文件名，不写入提交标题。第三方补丁保留原提交标题；本项目补丁采用对应 Linux 子系统的标题格式和语言习惯。

补丁维护遵守以下规则：

1. 下游修复的任何部分如果已有被主线、stable/LTS 维护树或对应子系统维护者集成树接受的等价实现，而目标内核尚未包含该实现，必须采用正式上游实现，不维护没有必要的平行实现。允许为适应目标内核进行必要的回移调整，但必须说明调整原因及与上游的差异。仍需在其基础上修复的问题，应撰写独立的下游补丁。 \
   维护基于 stable 或 LTS 版本的下游分支时，优先采用对应稳定分支已有的官方回移版本，将其视为本次回移的直接上游提交，并保留其原始主线提交的追溯信息。对应稳定分支尚无可用回移，或其回移版本与本树特有代码、特性不兼容时，再评估原始主线提交如何适配。 \
   回移单个提交前，应检查其所在补丁系列的前序补丁及相关修正，将同系列改动一并纳入适用性和依赖判断。回移时只引入必要的前置依赖，不为消除上下文冲突而顺带引入无关重构、格式调整或功能变更。

2. 回移时必须核对原分支与目标分支中被修改函数、结构体及其调用上下文，检查差异是否影响补丁语义。遇到函数名、参数或接口变化时，不能只做机械重命名；必须核对参数含义、返回值、错误路径、锁和资源生命周期，并沿相关调用链核对所用 API 的实现和行为。 \
   修改共享头文件中的函数接口、内联函数、宏或结构体时，必须在整个目标内核源码树中检查所有使用者，包括上游不存在或不再维护的厂商、下游代码。逐一核对调用点、字段访问、初始化及依赖结构体布局的代码，并同步调整受影响的使用者。

3. 邮件列表或其他仓库已有同类实现时，应优先评估复用，并按需要增加独立的下游补丁。是否采用现有实现，应根据正确性、主线方向、目标设计及依赖成本判断，不以差异大小机械决定是否重写。 \
   不强行移植与目标设计不兼容的实现。另行实现时，应说明不采用现有方案的具体原因；凡沿用第三方代码，仍须保留来源和相应作者贡献，不因大规模重构而归为纯原创。

4. 所有第三方来源的补丁保留原作者、原有 `Signed-off-by`，以及必要的版权和许可证声明。不得将他人的补丁改署为本项目作者，不得代原作者补加其未提供的 `Signed-off-by`。 \
   回移或适配者在能够满足 DCO 的情况下，可以添加自己的 `Signed-off-by`，并注明所作调整。不得将多作者补丁系列压成仅署一个作者的聚合补丁。

5. 每枚补丁只包含一个逻辑改动，按主线 Linux 及对应子系统的规范和习惯拆分。大量代码应触发拆分审查，但不按行数机械切割。 \
   新驱动或新模块的主体可以较大，但设备树绑定、驱动、设备树及独立功能仍应合理拆分。“新增模块”不构成混入多个独立改动的例外。补丁系列应在每一步保持可构建，不引入已知故障，便于定位回归。

6. 本项目自行撰写且尚未被上游接受的补丁，其原有功能中的缺陷应直接修回原补丁，禁止堆叠“修复本地补丁的补丁”。独立的新功能应另行拆分。 \
   已经邮件投稿的补丁，修正后应形成新版本并保留版本追溯。已经被上游接受的提交出现缺陷时，应撰写独立修复，并正确填写 `Fixes:`。 \
   修改原 `.patch` 文件仍应正常形成新的项目仓库提交；本条不要求改写已经公开的 Git 历史。

7. 补丁分类随实际状态更新。本项目补丁投稿后转入 `MAILLIST`，被正式接受后采用上游正式版本并转入 `UPSTREAM`。补丁应与引用的版本对应，必要的回移适配必须明确说明。 \
   升级内核基线时，删除已被基线包含或被正式上游实现取代的补丁，并重新检查后续依赖。来源补丁被撤销、替换或适用条件发生变化时，应重新评估，不因曾被接受而永久保留。

8. 补丁说明应完整描述问题、影响、修改理由、来源及验证方式，不能只依靠外部链接解释其必要性。补丁必须能在声明的内核基线及前置补丁之上干净应用。 \
   逐补丁需要编译验证时，使用目标配置和工具链，通过 Kbuild 只编译实际受影响的对象，不为每枚补丁重复构建整个内核。编译范围应包含间接受头文件、接口或结构体变更影响的对象，不限于补丁直接修改的文件。 \
   对跨目录接口、符号导出、Kconfig 或构建依赖的改动，应补充相关配置及必要的链接检查；补丁系列完成后，再用目标配置进行完整构建，并按需要进行实机验证。
